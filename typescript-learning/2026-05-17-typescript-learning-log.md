### 4.5 클래스와 데커레이터

- 타입스크립트에서 클래스는 객체 지향 설계를 구현하기 위한 강력한 문법.
- 데커레이터는 이러한 클래스의 동작을 동적으로 확장하고 수정할 수 있는 강력한 문법.

#### 4.5.1 클래스

* 접근 제한자(access modifier): 필드에 대한 접근을 제한하는 데 어디까지 제한을 할 것인지 정하는 것.

- UML(Unified Modeling Language): 통합 모델링 언어. 모델링을 할 때 사용되는 언어. 다양한 목적과 관점에 맞게 다이어그램을 도식화하는 데 주로 사용됨. 규모가 큰 프로젝트일수록 사전 설계를 꼼꼼히 하고, 설계를 할 때 UML을 가장 많이 채택함.

- 타입스크립트에서는 접근 제한자에 특별한 기능이 있음. 즉, **생성자 함수의 파라미터 앞에 접근 제한자를 달아주면 필드를 초기화하는 코드를 생략**할 수 있음.
- 접근 제한자

|:---:|:---:|:---:|:---:|
|:---:| public | protected | private |
| 외부에서 접근 | ○ | × | × |
| 자식이 접근 | ○ | ○ | × |
| 내부에서 접근 | ○ | ○ | ○ |
| UML상에서 표기 | + | # | - |

- ○ ×

- 파라미터(parameter): 함수가 값을 받을 때 쓰는 입구 변수.
- 인자(argument): 실제로 넣어주는 값.

- 일반적인 방식
```TypeScript
class User {
    private id: number;
    publick name: string;
    
    constructor(id: number, name: string) {
        this.id = id;
        this.name = name;
    }
}
```

- TypeScript의 축약 방식
```TypeScript
class User {
    constructor(
        private id: number,
        public name: string,
    ) {}
}
```

* 상황에 따라 천차만별이지만 실전 프로젝트에서 개발을 하면 필드값은 외부의 접근을 막기 위해 대부분 private으로 선언함. 필드값을 private로 선언하면 값을 설정하고 가져올 때 **세터(setter)**와 **게터(getter)**를 이용해야 함.

* compilerOptions에서 target 옵션을 ES6 이상으로 했을 때는 **private 접근 제한자를 생략하고 대신 필드에 #을 붙여줘도 동일한 의미**가 됨.

* 게터니는 'get <필드이름>'으로 세터는 'set <필드이름>'으로 선언하며 필드의 값을 가져올 때는 자동으로 게터가 호출되고, 값을 변경하면 자동으로 세터가 호출되어 값이 변경됨.
* '왜 귀찮게 private, getter, setter를 쓰지?'
    - 외부에서 임의로 값을 변경하는 것을 방지할 수 있음.
    - 데이터의 무결성을 지킬 수 있음.

- 필드: 객체 내부에 붙어 있는 값
- 필드 vs 메서드
    - 필드: 객체가 가진 데이터
    - 메서드: 객체가 할 수 있는 동작
    - 필드는 "상태/정보", 메서드는 "동작/기능"

* 타입스크립트에서 인터페이스는 다양한 용도로 사용할 수 있음. 특히 인터페이스와 클래스는 서로 떼려야 뗄 수 없는 관계.

- implements의 장점: 다중 상속이 가능해진다는 것.
- 타입스크립트에서 클래스는 단일 상속만 가능하지만, 인터페이스가 다중 상속이 가능하다는 것을 이용하면 설계상으로 다중 상속을 할 수 있음.
- **implements한 인터페이스는 반드시 구현**해야 하므로 재사용성이 높아지지는 않음.

#### 4.5.2 데커레이터

* 컴파일 타임 vs 런 타임
    - 컴파일 타임: TypeScript가 코드를 검사하는 시간. TypeScript 코드가 JavaScript 코드로 변환되기 전에, TypeScript가 코드를 검사하는 단계.
    - 런 타임 JavaScript 코드가 실제로 실행되는 시간

- 프로퍼티: 객체가 가지고 있는 값.
- 필드: 클래스 안에서 선언하는 객체의 데이터 자리.

* 데커레이터(decorator): 런타임에 실행되어 클래스, 메서드, 프로퍼티 등에 동적으로 메타데이터나 기능을 조작하는 기능.

* **데커레이터는 클래스 위에서 작동하는 문법이며 단독으로 사용하지 않기 때문**에 클래스를 하나의 예제로 만들어줌.
* 데커레이터는 클래스와 필드 위에 @함수명 꼴로 달아주면 됨.
* **데커레이터가 클래스가 선언될 때(init될 때) 런타임에서 실행됨.**

* **한 번 더 감싸주는 래퍼 함수를 추가해주면 인수로 원하는 데이터도 넘길 수 있으므로,** 원하는 로직을 완성할 수 있음. 이 문법은 차후에 NestJS로 백엔드 코딩을 할 때 라우팅 테이블을 만들고 다양한 미들웨어를 등록하는 원리가 됨.

* **데커레이터는 클래스, 메서드, 필드, 파라미터, 이렇게 총 4곳에 들어갈 수 있음.**

- 라우팅(routing): 사용자의 요청 주소를 보고, 어떤 코드로 보낼지 결정하는 것.
- 라우팅 테이블(routing table): 어떤 요청 주소가 어떤 함수와 연결되어 있는지 정리한 표.
- 미들웨어(middleware): 요청이 최종 함수에 도착하기 전에 중간에서 실행되는 코드.

* 기본적으로 데커레이터는 콘셉트 자체가 인수에 메타 정보가 넘어오는 콘셉트.

* 클래스 데커레이터도 메서드 테커레이터랑 똑같이 최상단에 래퍼 함수를 한 번 감싸주면 인수로 자신이 원하는 데이터를 넘길 수 있도록 설계되어 원하는 로직을 요구사항에 맞게 처리할 수 있도록 되어 있음.
* 생성자가 인수로 넘어왔다는 것은 내부까지 조작이 가능하다는 의미. 실제로 내부에 아무것도 없는 클래스임에도 생성자를 상속하여 데커레이터를 이용해서 인스턴스까지 조작할 수 있음.

### 4.6 제네릭

* 제네릭은 현대 프로그래밍에서 가장 중요한 개념 중 하나. 타입의 안정성을 보장함과 동시에 코드의 재사용성을 극대화해줌.

#### 4.6.1 제네릭 기본

* **제네릭(generic)**: 타입스크립트에서 인터페이스와 함께 가장 중요하다고 생각되는 문법. 타입스크립트뿐만 아니라 다양한 언어에서도 제네릭을 지원할 만큼 인기가 많은 분법이며, 현대 프로그래밍에 거의 필수라고 할 수 있음.

- 제네릭은 타입계의 함수라고 할 수 있음.

* 제네릭의 문법은 간단함. **홑화살괄호(<>) 안에는 함수 파라미터를 넣듯이** 타입을 넣어줌.
- 제네릭 역시 유연한 만큼 함수, 클래스, 인터페이스 등과 다양한 활용이 가능함.

#### 4.6.2 유틸리티 타입

* **유틸리티 타입(utility type)**: 기존에 있는 타입을 쉽게 변환할 수 있도록 도와주는 타입 문법.

- Awaited<T>, Promise<T>
- Partial<T>: 말 그대로 모든 프로퍼티를 옵셔널로 만듬.
- Readonly<T>: 말 그대로 모든 키에 readonly를 붙여줌.
- Omit<T, Keys>: T에는 원본 인터페이스 타입을 넣어두고 Keys에는 제외하고 싶은 프로퍼티를 나열하면 됨.

- 객체는 실제 데이터 덩어리, 클래스는 객체를 만들기 위한 설계도.
- interface는 extends 가능.
- type은 extends 불가능
- type에서는 확장 시, & 사용.
- type에서의 extneds는 조건 검사. type에서도 조건부 타입에서는 extends가 등장함.
